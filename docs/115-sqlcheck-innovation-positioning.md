# 115 年 SQLCheck 創新項目定位與產品語意

## 一、創新項目的核心問題

SQLCheck 的目標不是用生成式 AI 取代 Oracle DBA，也不是在沒有執行計畫、索引與統計資訊的情況下宣稱「改完一定更快」。

本專案要解決的是地方稅共用平台更實際的問題：

> 把既有 SQL 效能管理規範，轉化成同仁在 SQL 執行前就能理解、學習與改善的智慧輔助機制。

地方稅平台為共同使用環境。自撰 SQL 的寫法如果不妥，可能增加共用資源負擔，因此中心已要求自撰 SQL 應取得 execution plan、COST 小於 10 萬、具備查詢條件、依規範使用 index、先於測試環境測試，並禁止 Parallel Hint 等做法。

SQLCheck 將這些規範拆成確定性規則，再以地端 Gemma 4 31B 把技術結果翻成一般 SQL 撰寫同仁能理解的改善方向。

## 二、可對考核委員強調的創新價值

### 1. 從「事後審核」前移為「執行前智慧輔導」

傳統檢核工具回答「合不合規」。

SQLCheck 進一步回答：

- 哪一段值得注意？
- 為什麼？
- 可以怎麼調整？
- 這個建議能否直接採用？
- 哪些地方一定要先由業務人員確認？

### 2. AI 與規則引擎分工，避免幻覺直接成為 SQL

AI 負責白話解釋與提出改善方向。

程式規則負責：

- 中心規範判定
- COST / WHERE / Parallel Hint 等確定性檢核
- 可證明改寫的安全驗證
- 阻擋 AI 編造欄位、資料表或 JOIN 條件
- 對無法證明的改法清楚標示「需確認後再改」

這不是「相信 AI」，而是「讓 AI 在可控邊界內協助同仁」。

### 3. 地端生成式 AI

正式環境以地端 Gemma 4 31B 提供說明，不以雲端模型處理正式 SQL。

此設計的價值是：

- 保留生成式 AI 的自然語言說明能力
- 配合內部環境使用需求
- 透過 deterministic guard 降低模型幻覺風險

### 4. 從單次檢核變成 SQL 撰寫學習機制

畫面不只顯示 PASS / BLOCK，而是用「目前寫法 → 建議方向 → 採用狀態 → 建議寫法」讓同仁知道為什麼要調整。

長期目標是讓使用者逐步養成較佳的 SQL 撰寫習慣，從源頭降低不適當 SQL 進入正式環境的機會。

## 三、網頁語意原則

### 中心規範

只呈現正式規範的 PASS / BLOCK / NOTICE，不讓 AI 改判。

### 改善優先指數

回答：

> 這支 SQL 有多需要優先檢視？

完全由確定性規則、SQL 結構與 COST 計算；AI 不得加減分。

### 智慧改善建議

回答：

> 哪裡值得改、為什麼、下一步怎麼做？

每項建議使用：

- 改善機會：高／中／低
- 查詢結果已確認／系統已修正寫法／需確認後再改／需先確認

「改善機會」只是值得檢視的程度，不等於實際效能提升幅度。

### 建議採用狀態

回答：

> 上面的建議目前可以怎麼使用？

不再使用「預估改善效果」，避免讓使用者誤以為系統已量測改寫後效能。

### 原寫法與建議寫法

只在有具體 SQL 建議時顯示差異。

- 系統可證明查詢結果不變：清楚標示「查詢結果已確認」
- 無法證明：標示「示意方向（請勿直接套用）」
- 缺 WHERE、未知 JOIN key、未知資料型態等資訊不足案例：只提供文字方向，不為了畫面完整而猜 SQL

## 四、考核報告建議用語

建議創新名稱：

> **從規範檢核到智慧改善－地端 AI SQL 效能輔助機制**

核心敘述：

> 本局將財政資訊中心自撰 SQL 效能管理規範轉化為系統化檢核規則，並導入地端生成式 AI，於 SQL 執行前提供白話化改善說明及建議寫法。系統採「規則判定、AI 說明、程式複核」三層機制，對可證明不改變查詢結果之特定寫法提供建議改寫；涉及未知欄位型態、業務查詢範圍或資料表關聯時，則不由 AI 猜測，而明確提示需確認事項，使生成式 AI 的便利性與資料庫治理要求並行。

## 五、成效證據原則

年度報告應優先放可驗證的實際數據，而不是模型猜測的百分比。

建議年度結算後填列：

- SQLCheck 實際檢核件數：【待填】
- 命中中心規範提醒／不符合件數：【待填】
- 提供智慧改善建議件數：【待填】
- 系統確認完整建議改寫件數（rewrite_outcome=provided）：【待填】
- 建議片段經系統確認／修正件數（verification=verified/corrected）：【待填】
- 建議片段需人工確認件數（verification=unverified 或無可直接套用範例）：【待填】
- 具代表性的 SQL 於測試環境調整前後 COST：【待填】
- 具代表性的 SQL 於測試環境調整前後執行時間或資源觀察：【待填】
- 使用者回饋或教育宣導成效：【待填】

上述檢核、改寫與 verification 狀態可由去識別化 archive 統計；實際效能成效仍應以代表性 SQL
在測試環境的前後比較作為佐證。只有實際取得測試證據後，才寫「降低 COST」「縮短執行時間」
或「提升多少百分比」。

在尚未取得實測數據時，宜使用：

- 「提供改善方向」
- 「降低不適當 SQL 進入正式環境之機會」
- 「協助同仁於執行前辨識可改善寫法」
- 「將規範轉化為即時、可理解的操作指引」

而不要寫：

- 「保證提升 XX% 效能」
- 「AI 已確認會使用索引」
- 「一定避免 Full Table Scan」
- 「改寫後 COST 一定下降」
